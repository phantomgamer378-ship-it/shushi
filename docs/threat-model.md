**Document**: Threat Model & Security Architecture Document  
**Methodology**: STRIDE (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege)

## 1. Threat Matrix & Detailed Mitigations

| Threat # | Threat Category | Threat Description | Attack Vector / Scenario | Concrete Mitigation Strategy | Verification & Test Scenario |
| :---: | :--- | :--- | :--- | :--- | :--- |
| **TH-01** | **Spoofing / Tampering** | Forged webhook requests | Adversary sends fake registration payloads directly to `/v1/webhooks/google-forms` bypassing Google Forms. | Enforce per-event secret key. Apps Script signs payload with `HMAC-SHA256(secret, body)`. Backend validates via `hmac.compare_digest`. | Send `POST /v1/webhooks/google-forms` with an invalid signature. Verify API rejects with `400 Bad Request` and logs security warning. |
| **TH-02** | **Tampering / Replay** | Webhook replay attacks | Attacker intercepts a valid signed webhook and replays it repeatedly to corrupt state or spam outbox. | Enforce `X-Webhook-Timestamp` header. Reject requests with drift $> 300$ seconds. Store unique `form_response_id` in `webhook_receipts`. | Intercept valid webhook; replay with a 6-minute expired timestamp. Verify rejection with `CLOCK_DRIFT_EXCEEDED`. Replay within window; verify idempotent 200 no-op. |
| **TH-03** | **Tampering** | Duplicate registrations | Attendee or automated bot submits multiple RSVPs to exhaust ticket capacity. | Database-level unique constraint `UNIQUE (event_id, attendee_email) WHERE status != 'CANCELLED'`. Application validates email uniqueness before insertion. | Submit two distinct form responses with identical email for the same event. Verify second registration fails or links to existing ticket without double capacity increment. |
| **TH-04** | **Information Disclosure** | QR token theft from DB or logs | Attacker gains read-only access to database, backup, or application logs and steals valid QR tokens. | Raw tokens are NEVER stored in the `tickets` table; only one-way `SHA-256(raw_token)` is persisted. Zero raw tokens logged. Outbox encrypted via AES-256-GCM. | Run DB query `SELECT * FROM tickets`; confirm only 64-char hex SHA-256 hashes exist. Inspect all application logs; confirm zero raw tokens appear. |
| **TH-05** | **Tampering** | Ticket cloning & duplication | Attendee screenshots QR code and shares with multiple people to gain multiple admissions. | Strict atomic consumption at database level. `SELECT FOR UPDATE` on `tickets` row. Database unique constraint on `check_ins(ticket_id)`. | Fire two concurrent check-in HTTP requests with the exact same QR token at the exact same millisecond. Verify exactly one returns `200 ADMITTED` and the other returns `409 ALREADY_CHECKED_IN`. |
| **TH-06** | **Elevation of Privilege** | Unauthorized check-in | Attacker attempts to hit check-in endpoint without valid staff credentials. | Require Supabase Auth JWT. Fast check-in dependency verifies caller identity in `event_staff` table with `role IN ('owner', 'admin', 'staff')`. | Call `POST /v1/events/{id}/check-in` anonymously and with non-staff JWT. Verify `401 Unauthorized` and `403 Forbidden` respectively. |
| **TH-07** | **Elevation of Privilege** | Cross-event access (IDOR) | Staff member authorized for Event A attempts to scan tickets or view attendee data for Event B. | Enforce strict event-scoped multi-tenancy. Every request requires `event_id` URL parameter validated against caller's `event_staff` membership. | Staff user assigned to Event A issues `GET /v1/events/B/registrations`. Verify backend returns `403 Forbidden`. |
| **TH-08** | **Spoofing** | JWT misuse / forging | Attacker creates forged JWT or uses expired token to access administrative endpoints. | Use Supabase Auth asymmetric public key verification (`RS256` or secure `HS256` secret verification). Reject expired tokens (`exp` check). | Submit request with unsigned, tampered, or expired JWT. Verify rejection with `401 Unauthorized`. |
| **TH-09** | **Tampering** | SQL injection | Attacker injects SQL payloads into form fields or search queries. | 100% parameterized queries via SQLAlchemy 2.0 ORM and Pydantic v2 strict type validation. Raw string SQL concatenation is strictly forbidden. | Send SQL injection string (`' OR '1'='1`) into attendee name, search parameter, and form fields. Verify string is treated as literal text and causes no syntax or logic anomalies. |
| **TH-10** | **Denial of Service** | Brute-force scanning | Attacker sends high-frequency random tokens to check-in endpoint hoping to guess a valid ticket. | 256 bits of entropy in token (`secrets.token_urlsafe(32)`) yields $2^{256}$ keyspace (brute force impossible). Rate-limit check-in endpoint to 20 req/s per staff device. | Benchmark token entropy calculation. Trigger rapid successive invalid scan attempts from single IP/device; verify rate-limiter returns `429 Too Many Requests`. |
| **TH-11** | **Information Disclosure** | Sensitive information leakage (PII) | QR code contains attendee personal information, readable by any phone camera. | QR payload strictly encodes the raw opaque random string. Zero PII (no name, email, phone) encoded in QR. Scanner queries backend to resolve attendee name upon check-in. | Scan QR code with generic mobile camera scanner. Verify payload contains only an unguessable opaque random string, without any human-readable PII. |
| **TH-12** | **Denial of Service** | Email abuse & spamming | Attacker floods form with target email addresses to weaponize Resend email dispatcher. | Event capacity enforcement, rate-limiting on webhook ingestion, and domain-level email sanitization. Outbox limits retries to 5 attempts before `DEAD_LETTER`. | Attempt to flood 1,000 requests to closed or full event. Verify requests are rejected before entering `email_outbox`. Verify failing emails hit dead-letter after 5 retries. |
| **TH-13** | **Denial of Service** | Application & DB DoS | Heavy traffic spikes at event start overwhelm database connections. | Supabase Supavisor connection pooling (port 6543) caps active connections. Database queries strictly use indexed columns (`token_hash`, `form_response_id`). | Run concurrency stress test with 100 simultaneous simulated check-ins. Verify connection pool handles load without crashing or dropping transactions. |

## 2. Threat Modeling Review Sign-off

- **Attack Surface Analysis**: Webhook ingestion is protected with symmetric HMAC-SHA256 and timestamp anti-replay. Check-in operations are guarded by Supabase Auth and event-scoped RBAC.
- **Fail-Closed Principle**: Scanner clients and API endpoints default to fail-closed behavior on network timeouts or unexpected errors.
- **Defense in Depth**: Database constraints (unique `ticket_id` in `check_ins`) provide hard boundary security even if application code were compromised.
